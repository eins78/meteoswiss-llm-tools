## VERDICT: ✅ PROMOTE

**No functional failure and no performance regression found.** 120/120 checks pass on TEST, and the
99-check subset run against PROD 3.1.0 also passes 99/99. All 47 comparable search/fetch payloads are
byte-identical between 3.1.0 and 3.1.1-rc.0, including 27 converted pages in four languages.

Recommendation: merge #157 and release `3.1.1`. Two things to decide, neither blocking:

1. **A client-visible change is missing from the changelog.** Input-validation error text changed
   (see W1). Add a line to the changeset if you want it documented.
2. **The TEST deploy automation is broken** (see I1). The release is fine, but the next RC will not
   reach TEST by itself until `meteoswiss-deploy.sh` is fixed.

## Performance

TTFT is time to the first response byte. These servers answer with a single JSON body, so **TTFT
equals total time**; there is no streaming to separate them. Timings are client-side against
`localhost`.

### Sequential, TEST 3.1.1-rc.0

| Tool | n | median | p95 |
|---|---|---|---|
| protocol calls | 8 | 2 ms | 15 ms |
| `search` | 13 | 23 ms | 51 ms |
| `fetch` (first fetch of 27 pages) | 27 | 135 ms | 347 ms max |
| `fetch` (cached repeat) | 3 | 2 / 2 / 1 ms | |
| `meteoswissCurrentWeather` | 23 | 6 ms | 88 ms |
| `meteoswissStations` | 5 | 1 ms | 2 ms |
| `meteoswissPollenData` | 3 | 4 ms | 72 ms |
| `meteoswissClimateData` | 8 | 46 ms | 100 ms |
| `meteoswissLocalForecast`, cold container | 11 | 11.8 s | 9.7–15.8 s |

PROD 3.1.0 comparison for first-time `fetch`: 107–199 ms per page (first PROD run), against 103–347 ms
(median 135 ms) on TEST. The other PROD numbers in the saved run are cache-warm and not comparable
(`fetch` median 5 ms), so they are deliberately not tabulated.

### 8 concurrent sessions, `meteoswissLocalForecast`

First on TEST's own container, three waves: wall **109.3 s, 109.9 s, 110.5 s**, 0/8 failed, 0 `ENOENT`.
That is slower than the 79–87 s recorded for 3.1.0-rc.0 on 2026-09-11, but the host was busy this
time (load average 5.7 → 9.6, with the `madek-perf` benchmark containers running), so it was not
trusted as a comparison. A controlled A/B followed: identical throwaway containers of 3.1.0 and
3.1.1-rc.0, alternating, same host, same minute:

| Round | 3.1.0 wall | 3.1.1-rc.0 wall |
|---|---|---|
| 1 | 116.4 s | 115.2 s |
| 2 | 157.1 s | 105.4 s |

0/8 failed in all four. **No regression**: the RC was equal or faster in both rounds, and the spread
inside one version (116 vs 157 s) is larger than the difference between versions. Absolute 8-way
forecast latency (~105–157 s) is dominated by CSV parsing on a single event loop, as already logged in
`2026-09-11-rc-release-3.1.0-rc.0.md`; this release did not change it.

## Warnings and observations

### W1 — Validation error text changed (SDK 1.32.1), not in the changelog
Same invalid input, different message:

```
3.1.0:        …Invalid arguments for tool search: [\n  {\n    "code": "invalid_value",\n    "values": ["de","fr","it","en"] …
3.1.1-rc.0:   …Invalid arguments for tool search: Language must be one of: 'de' (German), 'fr' (French), 'it' (Italian), or 'en' (English). at language
```

Still `isError` with code `-32602`. The new text is shorter and easier for a model to read. Any client
that parses the old embedded JSON array would break. Nothing in this repo does. Worth one changelog
line.

### W2 — jsdom major bump is undocumented
Not mentioned in the 3.1.1 changelog. No behavioural effect found (above).

### N1 — Rate limit and test pacing
A ~100-call burst from one IP trips the 100 req/60 s limit. That is expected (limiter code is
unchanged), and the suite waits out the window and retries. It happened once on TEST, and six times on
a throwaway container before the suite learned to wait (four of those became false "failures").

### N2 — Earlier reports are stale on `fetch`
The rc4 report says `fetch` takes `url`. Current schema (`tools/list`): **`id`** (plus `format`,
`includeMetadata`). `url` is rejected.

### N3 — Not covered
`mcp-remote` 0.8.0 and `@modelcontextprotocol/inspector` 2.x (both devDependencies only, not shipped
in the image); Claude Desktop; the public Caddy/BLN hostname (tests ran against `localhost`).

## Infrastructure finding (not a defect in the RC)

### I1 — `meteoswiss-deploy.sh` cannot change the compose file, so the poller never deployed the RC

> **Update, same day (after this report was written):** fixed in docker-infra `8bd73a1`. The real
> cause of the off-by-5 is that yq v4 strips the file's leading comment block before parsing, so every
> reported line is short by the header's length; a 5-line header was added on 2026-09-20 (`059817b`).
> The script now finds the line with awk and aborts unless only the target service changed. With it,
> `meteoswiss-deploy.sh test 3.1.1` and `meteoswiss-deploy-prod.sh 3.1.1` both recreated their service
> and passed the health check on the first attempt. The text below is the original diagnosis.

The LaunchAgent `li.kiste.meteoswiss-deploy` is loaded (300 s interval, healthy) and detected the RC
at 16:47:26. Its deploy then failed and rolled back at 16:48, and kept doing so every 5 minutes.

Cause: `set_compose_image` (docker-infra `18ae2c2`) finds the line with `yq '<path> | line'`. On the
current `docker-compose.yaml` yq returns **237** for the TEST image (real line **242**) and **210** for
PROD's (real **215**), both off by 5. `sed '237s|3.1.0|3.1.1-rc.0|'` matches nothing and exits 0, the
guard (numeric and non-zero) passes, and `docker compose up -d` correctly prints `Container
meteoswiss_mcp_server_test Running`. Evidence from the log lines (16:53:36 attempt): "Updating
compose" and "Running" in the same second, then 12 health checks of "version mismatch (got 3.1.0,
want 3.1.1-rc.0)". `docker events` showed no stop/create/start. The rollback uses the same function,
so it is a silent no-op as well. Lines 237 and 210 are a comment and a volume entry, so nothing was
damaged.

Ruled out: the RC image itself (a throwaway container reports `version 3.1.1-rc.0` in `/health` and
in `package.json`), and compose (a `--dry-run` against a scratchpad copy with the changed line says
`Recreate`).

Workaround used: line 242 edited by hand (TEST only) and `docker compose up -d
meteoswiss_mcp_server_test`; the poller's next cycle then saw "already running" and wrote
`meteoswiss-mcp-v3.1.1-rc.0` to `.meteoswiss-last-rc-tag`. **Not fixed:** the script still has the
bug, and the compose edit is not yet committed to docker-infra.

Suggested fix: find the line by the service header (awk for `^  <service>:` then the first
`^    image:`), and after the `sed`, abort if `yq '<path>'` does not equal the new image. Add a
`--self-test` case on the real compose file; the existing fixture is too small to show the offset.
