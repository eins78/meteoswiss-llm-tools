# Handling Pre-Releases with Changesets

> How [@changesets/cli](https://github.com/changesets/changesets) supports pre-release versioning (pre mode vs. snapshot releases), the pitfalls each mode carries in CI, and an exact, verified command sequence for cutting an `-rc.1` release from this repo's open PR [#117](https://github.com/eins78/meteoswiss-llm-tools/pull/117).

## Key Facts

- **Decision:** none required to read this — it's reference material for whoever cuts the first RC of `meteoswiss-mcp@3.0.0`. Max reviews and decides whether/when to ship an RC before merging PR #117 as a stable release.
- **The first pre-release version is `-rc.0`, not `-rc.1`.** Changesets' prerelease counter starts at zero. `pnpm changeset pre enter rc` followed by one `pnpm changeset version` run produces `3.0.0-rc.0`; a **second** `version` run (after adding or merging another changeset) produces `3.0.0-rc.1`. There is no built-in way to start the counter at `1`. **Verified empirically** in this worktree — see [§3](#3-walkthrough-cutting-an-rc-from-pr-117-verified).
- **This repo does not run `changeset publish` anywhere.** `version-packages.yml` only wires the `version` step of [`changesets/action`][ref-S4]; publishing is triggered by **creating a GitHub Release**, which `release.yml` picks up. That workflow already contains prerelease-aware branching (`npm publish --tag next` instead of default `latest`, and no Docker `:latest` tag) — see [§3](#3-walkthrough-cutting-an-rc-from-pr-117-verified).
- **Entering pre mode is what turns PR #117 into an RC PR.** #117 currently proposes a *stable* `meteoswiss-mcp@3.0.0` + `meteoswiss-skills@1.1.0`. It does not become a release-candidate PR on its own — pushing `.changeset/pre.json` to `main` is the action that makes `changesets/action` regenerate #117 with `-rc.0` suffixes.
- **While `.changeset/pre.json` sits on `main`, every changeset merged after it becomes another prerelease** — stable releases are blocked until `changeset pre exit` runs and a `version` step executes afterward ([official warning][ref-S1], real-world confirmation in [Apollo Client's writeup][ref-S5]).

## Glossary

- **Pre mode** — a changesets state, toggled by `.changeset/pre.json`, in which every `changeset version` run appends a prerelease suffix (`-<tag>.N`) instead of bumping to a stable version. [[docs]][ref-S1]
- **Snapshot release** — a one-off, ephemeral version (`0.0.0-<tag>-<timestamp>`) generated by `changeset version --snapshot`, independent of pre mode and typically used for per-commit/per-PR builds. [[docs]][ref-S2]
- **`pre.json` / `PreState`** — the file `.changeset/pre.json`, created by `changeset pre enter <tag>` and deleted by `changeset pre exit`. Holds `mode` (`"pre"` or `"exit"`), `tag`, `initialVersions` (versions when pre mode was entered), and `changesets` (names of changeset files already folded into the current prerelease count). [[type ref]][ref-S3]
- **dist-tag** — an npm registry label (`latest`, `next`, etc.) pointing at a specific published version. `npm install pkg` resolves `latest` by default; `npm install pkg@next` is explicit.
- **Version Packages PR** — the standing PR that [`changesets/action`][ref-S4] keeps open/updated on every push to `main`, running the configured `version` script and proposing the resulting `package.json`/`CHANGELOG.md` diffs. PR #117 in this repo is that PR.
- **rc.N counter** — the integer changesets appends after a prerelease tag (`-rc.0`, `-rc.1`, …). It increments by one on every `changeset version` run while pre mode is active; it does **not** reset when new changesets are added mid-prerelease.

## 1. Standard mechanisms

Changesets offers three distinct paths to a pre-release. They solve different problems and are not really substitutes for each other.

### 1.1 Pre mode (`changeset pre enter` / `changeset pre exit`)

The built-in, stateful mechanism for a **sustained** pre-release cycle (beta/rc period before a real release).

```bash
changeset pre enter rc      # writes .changeset/pre.json, mode: "pre", tag: "rc"
changeset version           # every pending changeset becomes part of -rc.0
                             # (or -rc.N on a later run — see §1.4)
changeset publish            # publishes the prerelease version to npm under
                             # dist-tag "rc" (never "latest")
# ... repeat version+publish for -rc.1, -rc.2, ... as more changesets land ...
changeset pre exit           # deletes pre.json, un-flags pre mode
changeset version            # next run produces the real stable version,
                             # consuming everything accumulated during pre mode
```

The [official walkthrough][ref-S1] runs this exact sequence (with `yarn` in place of the repo's `pnpm`) and documents the resulting versions concretely:

> Starting with `pkg-a@1.0.0`, `pkg-b@2.0.0`, `pkg-c@3.0.0` … after `pre enter next` + `version` + `publish`: `pkg-a@1.0.1-next.0`, `pkg-b@2.1.0-next.0`, `pkg-c` stays at `3.0.0` (no changeset touched it). A second `version` + `publish` cycle (new changesets added) yields `pkg-a@1.1.0-next.1`, `pkg-c@3.0.1-next.0`, `pkg-d@1.0.0-next.0`. Exiting (`pre exit` + `version` + `publish`) finalizes `pkg-a@1.1.0`, `pkg-b@2.1.0`, `pkg-c@3.0.1`, `pkg-d@1.0.0`. [S1][ref-S1]

Key mechanics:
- **Independent per-package counters.** A package only gets a prerelease bump if it has a pending changeset; unaffected packages stay put (see `pkg-c` staying at `3.0.0` above).
- **Dependency ripple.** Prerelease versions like `5.1.0-next.0` don't satisfy a normal semver range like `^5.0.0`, so `changeset version` in pre mode may bump dependent packages that wouldn't normally need a bump, just to keep the workspace resolvable. [[S1]][ref-S1]
- **`changeset publish` auto-tags.** In pre mode, publish uses the prerelease tag as the npm dist-tag automatically — it does not touch `latest`.

**When to use it:** a genuine pre-release *period* — cutting rc.0, rc.1, rc.2 while stabilizing a real upcoming version, exactly the `-rc.1` scenario this report was asked to walk through.

### 1.2 Snapshot releases (`changeset version --snapshot` / `changeset publish --tag`)

A **stateless**, one-shot mechanism with no `pre.json`, no "mode," and no ongoing counter — designed for ephemeral per-commit or per-PR test builds.

```bash
changeset version --snapshot           # → 0.0.0-TIMESTAMP        (default)
changeset version --snapshot bulbasaur # → 0.0.0-bulbasaur-TIMESTAMP
changeset publish --tag bulbasaur      # publish under dist-tag "bulbasaur",
                                        # NEVER "latest"
```

The version format is deliberately unmoored from the package's real semver — `0.0.0-<tag>-<timestamp>` by default, or a custom base if a `snapshot` block is added to `.changeset/config.json` (this repo's config has none, so the plain `0.0.0-...` form applies if snapshots were adopted here). [[S2]][ref-S2]

The [snapshot docs][ref-S2] are blunt about the one rule that matters:

> By using the `--tag` flag, you will not add it to the `latest` flag on npm. This is REALLY IMPORTANT because if you do not include a tag, people installing your package using `yarn add your-package-name` will install the snapshot version. [S2][ref-S2]

**When to use it:** a "build a real installable package from this exact commit/PR, for reviewer or Renovate-adjacent testing" workflow — usually wired to run automatically on every open PR. It does **not** compose with a long-lived rc/beta cycle; there's no `-rc.N` sequencing, and you must never merge the versioned commit into a real branch. [[S2]][ref-S2]

### 1.3 Manual approaches

Outside the two built-ins, teams sometimes hand-roll pre-releases: manually editing `package.json` versions with a `-beta.N` suffix and running `npm publish --tag beta` directly, or scripting `npm version prerelease --preid=rc`. This sidesteps `changeset version`'s changelog generation and dependency-bump propagation entirely, so it's normally reserved for one-off emergency publishes where changesets' bookkeeping isn't wanted — not recommended as a repeatable pattern, and not applicable here since this repo already has changesets fully wired.

### 1.4 Which to use when

| Need | Mechanism |
|---|---|
| A sustained rc/beta period before a real release (this repo's ask) | **Pre mode** |
| One-off installable build tied to a specific commit/PR, for manual QA | **Snapshot** |
| Everything else | Stick with standard `changeset version` / stable releases |

## 2. Best practices and pitfalls

### 2.1 `pre.json` — what it tracks, and where it should live

`pre.json` records `mode`, `tag`, `initialVersions` (a snapshot of every package's version *at the moment pre mode was entered*, used to compute prerelease bumps), and `changesets` — the list of changeset filenames already folded into the running prerelease count. **Verified empirically** ([§3](#3-walkthrough-cutting-an-rc-from-pr-117-verified)): those listed changesets are **not deleted** from `.changeset/*.md` while pre mode is active — `changeset version` keeps re-reading and re-applying them on every run, and they're only consumed (files deleted) by the *first stable* `version` run after `pre exit`. This differs from a normal (non-pre) `changeset version` run, which deletes each changeset file as it's folded into the changelog.

**Should `pre.json` be committed?** Yes, but the location matters:
- **Committed to `main`** (the official docs' assumption) works for small teams with a single release stream, but means main is "poisoned" for stable releases the whole time it's there — see 2.3.
- **Committed only to a release branch, never `main`** is what [Apollo Client's automated release pipeline][ref-S5] settled on, specifically to avoid this lock-out:

  > I wanted to avoid ever committing `pre.json` to `main` … [Apollo] enters prerelease mode automatically on `release-x` branches … exits through a dedicated workflow that removes the `pre.json` file and reverts package versions to the last released state on main. [S5][ref-S5]

  They back this with a dedicated `check-prerelease.yml` guard workflow specifically to catch an accidental merge of `pre.json` into `main`.

### 2.2 Version Packages PR behavior in pre mode

`changesets/action` doesn't distinguish pre mode as a separate concept — it just runs whatever `version` script you give it (`pnpm run version` here) and diffs the result into the standing Version Packages PR. Concretely: **the instant `pre.json` lands on the branch the action watches, the *next* action run regenerates the existing Version Packages PR with `-<tag>.N` suffixes instead of stable versions** — same PR, same branch (`changeset-release/main` in this repo), different diff. There's no separate "prerelease PR" — it's the same mechanism, driven purely by whether `pre.json` exists when `version` runs.

### 2.3 The central pitfall: accidental lock-out of stable releases

Both the [official docs][ref-S1] and the [Apollo writeup][ref-S5] converge on the same warning, independently:

> If you decide to do prereleases from the default branch … without a branch for your last stable release, you will block other changes until exit. [S1][ref-S1]

Concretely: once `pre.json` is on `main`, *any* changeset that lands on `main` afterward — even one entirely unrelated to the RC effort — gets folded into the next prerelease bump instead of a normal release. A contributor merging an unrelated bugfix during the RC window will unknowingly ship it as `3.0.0-rc.3`, not `2.3.3`. The only way out is `changeset pre exit` + a `version` run, and that step is manual (nothing in this repo's CI runs it automatically).

**Avoiding an accidental stable release** during the RC window is the mirror-image risk: if someone runs `changeset version` locally on a branch where `pre.json` was never pulled, or `pre exit` gets triggered prematurely (e.g. a stray commit reverts `pre.json`), the next release PR silently reverts to proposing a stable version — easy to miss in review since the PR diff looks superficially similar. The safeguard is simple: **always check `git status`/`.changeset/pre.json` presence before merging a Version Packages PR**, and treat the PR's proposed version string (`-rc.N` vs. plain) as the first thing to sanity-check in review.

### 2.4 Snapshot vs. pre mode for CI-driven publishing

| | Pre mode | Snapshot |
|---|---|---|
| State | Persistent (`pre.json` on a branch) | None — stateless per invocation |
| Version shape | `<next-real-version>-<tag>.N`, sequential | `0.0.0-<tag>-<timestamp>`, unrelated to real semver |
| Fits "sustained rc.0 → rc.1 → rc.2 → stable" | Yes — this is what it's for | No — no cross-run sequencing |
| Fits "every PR gets an installable build" | Awkward — would need one enter/exit per PR | Yes — this is what it's for |
| Requires a `publish` step in CI | Yes (`changeset publish`) | Yes (`changeset publish --tag`) |
| **Fits this repo today** | Yes, with a manual publish trigger (see §3) | **No** — nothing in this repo's CI runs `changeset publish`; adding snapshot support would mean building a new publish workflow from scratch |

This repo's existing CI (`release.yml`) is triggered by **GitHub Release creation**, not by `changeset publish`. Pre mode composes with that model cleanly (an RC's `package.json` version, once merged to `main`, is just tagged and released like any other version — `release.yml` already branches on whether the tag string contains a `-suffix`). Snapshot releases would require a net-new "publish this snapshot version to npm" workflow this repo doesn't have, since `changeset publish` is never invoked anywhere in `.github/workflows/`.

## 3. Walkthrough: cutting an RC from PR #117 (verified)

### 3.0 How this repo is actually wired

Read directly from the repo, not inferred:

- **Monorepo**, pnpm workspaces (`packages/*`, `meteoswiss-forecast-evals` excluded) — [`pnpm-workspace.yaml`](../../pnpm-workspace.yaml). Two publishable packages: `meteoswiss-mcp` (npm, public) and `meteoswiss-skills` (validated as a Claude/Cursor plugin, **not published to npm**).
- **`.changeset/config.json`**: `access: "public"`, `baseBranch: "main"`, `fixed: []`, `linked: []` (independent versioning — no `snapshot` block configured).
- **Custom `version` script** (root [`package.json`](../../package.json)): `changeset version && node scripts/sync-skill-manifest-versions.mjs && node scripts/stamp-changelog-dates.mjs` — composes transparently with pre mode; it's just `changeset version` under the hood plus two repo-specific sync steps.
- **[`.github/workflows/version-packages.yml`](../../.github/workflows/version-packages.yml)** runs [`changesets/action`][ref-S4] with only `version: pnpm run version` set — **no `publish:` input**. This is the workflow that maintains PR #117.
- **Publishing is triggered by creating a GitHub Release**, not `changeset publish`:
  - [`.github/workflows/release.yml`](../../.github/workflows/release.yml), gated on `startsWith(github.event.release.tag_name, 'meteoswiss-mcp-v')`, already detects a prerelease tag via `^[0-9]+\.[0-9]+\.[0-9]+-.+` and runs `npm publish --access public --provenance --tag next` (instead of the default `latest`), and skips adding the Docker `:latest` tag — this infra was **already prerelease-aware before this research started**.
  - [`.github/workflows/release-skill.yml`](../../.github/workflows/release-skill.yml), gated on `meteoswiss-skills-v*`, only runs `pnpm --filter meteoswiss-skills test` — **no `npm publish` step at all**. A skills "RC" is a git tag + validation run, not a registry publish.
- **PR #117** ("Version Packages", branch `changeset-release/main`) currently proposes **stable** `meteoswiss-mcp@3.0.0` (major bump — breaking `meteoswissLocalForecast` shape change) and `meteoswiss-skills@1.1.0`, built from 10 pending changeset files in `.changeset/`.

### 3.1 Empirically verified version outputs

Running `pnpm changeset pre enter rc && pnpm run version` in this worktree (then fully reverting — no commit made) produced, exactly:

```
meteoswiss-mcp:     2.3.2  →  3.0.0-rc.0
meteoswiss-skills:  1.0.0  →  1.1.0-rc.0
```

with CHANGELOG headers stamped `## 3.0.0-rc.0 - 2026-07-16` / `## 1.1.0-rc.0 - 2026-07-16`, and `sync-skill-manifest-versions.mjs` propagating `1.1.0-rc.0` into all four skill manifest mirrors (`.claude-plugin/plugin.json`, `.claude-plugin/marketplace.json`, `.cursor-plugin/plugin.json`, `skills/meteoswiss-ogd/SKILL.md`). The individual `.changeset/*.md` files were **not** deleted — `.changeset/pre.json`'s `changesets` array recorded all 10 names instead, confirming §2.1's claim.

**The first RC is `-rc.0`, not `-rc.1`.** To reach `-rc.1`, a second `changeset version` run is needed — triggered by adding (or merging) at least one more changeset while still in pre mode.

### 3.2 Recommended path: commit only `pre.json`, let CI do the rest

```bash
# from repo root, on main, with a clean tree
pnpm changeset pre enter rc
git add .changeset/pre.json
git commit -m "ci: enter changesets prerelease mode (rc)"
git push
```

Pushing to `main` triggers `version-packages.yml`. `changesets/action` reruns `pnpm run version`, sees `pre.json`, and **regenerates PR #117 in place** (same branch, `changeset-release/main`) proposing:

```
meteoswiss-mcp@3.0.0-rc.0
meteoswiss-skills@1.1.0-rc.0
```

Merge that PR into `main` as you would any Version Packages PR — `package.json` on `main` now reads `3.0.0-rc.0` / `1.1.0-rc.0`.

**Publish by creating GitHub Releases** (this repo's actual publish trigger, not `changeset publish`):

```bash
gh release create meteoswiss-mcp-v3.0.0-rc.0 \
  --title "meteoswiss-mcp v3.0.0-rc.0" \
  --notes "Release candidate — see packages/meteoswiss-mcp/CHANGELOG.md" \
  --prerelease --target main

gh release create meteoswiss-skills-v1.1.0-rc.0 \
  --title "meteoswiss-skills v1.1.0-rc.0" \
  --notes "Release candidate — see packages/meteoswiss-skills/CHANGELOG.md" \
  --prerelease --target main
```

The first tag fires `release.yml`: its regex match on `-rc.0` sets `prerelease=true`, so it runs `npm publish --access public --provenance --tag next` (installable via `npm install meteoswiss-mcp@next`, `latest` untouched) and pushes the Docker image tagged `3.0.0-rc.0` only (no `:latest`). The second tag fires `release-skill.yml`'s validation job only — there is no npm package to wait for.

### 3.3 Getting to `-rc.1`

Still inside pre mode (`.changeset/pre.json` still present on `main`), add or merge one more changeset — e.g. a fix found while testing `rc.0` — and let `version-packages.yml` run again (any push to `main` re-triggers it). PR #117 regenerates a second time, now proposing `3.0.0-rc.1` / `1.1.0-rc.1` (skills only bumps if it has a new changeset too — otherwise it stays at `rc.0`). Merge and tag `meteoswiss-mcp-v3.0.0-rc.1` the same way as §3.2.

### 3.4 Exiting pre mode

Once satisfied with the RC:

```bash
pnpm changeset pre exit
git add .changeset/pre.json   # will show as deleted
git commit -m "ci: exit changesets prerelease mode"
git push
```

The next `version-packages.yml` run regenerates PR #117 one final time — now a **stable** `3.0.0` / `1.1.0`, and this run is the one that actually deletes the consumed `.changeset/*.md` files (per §3.1/§2.1). Merge it, then release `meteoswiss-mcp-v3.0.0` and `meteoswiss-skills-v1.1.0` exactly as in §3.2 — `release.yml`'s regex won't match a plain `X.Y.Z` tag, so it publishes to `latest` and tags Docker `:latest` as normal.

### 3.5 The one repo-specific risk to flag before doing this

Per §2.3: from the moment `.changeset/pre.json` is pushed to `main` until `pre exit` is pushed, **any other changeset merged to `main` becomes part of the next `-rc.N`, not a normal patch/minor release.** Given this repo has a single active branch and a solo-maintainer merge cadence (`main` only, no dedicated release branch, and a standing policy that only Max merges), the on-`main` approach in §3.2–3.4 is reasonable **as long as the RC window stays short and no unrelated changeset lands mid-window** — check `.changeset/pre.json` presence before merging anything else while an RC is in flight. Apollo's branch-isolated approach (§2.1) is the safer pattern at higher merge velocity or with multiple contributors, but is more machinery than this repo's current release cadence needs.
