# Cutting 3.1.1-rc.0 from PR #157 without a merge, and finding why the poller could not deploy it

**Date:** 2026-10-11
**Source:** Claude Code (Opus 5.5), delegated from homebot
**Session:** Max asked for an RC of what the Version Packages PR (#157) would release, deployed to TEST,
with a full manual test suite. Constraints from the brief: do not merge #157, no stable release, never
touch PROD, and stop and report before any merge into `main`.

Test report: `docs/research/2026-10-11-3.1.1-rc.0-rc-test-report.md`.

## Summary

`meteoswiss-mcp@3.1.1-rc.0` is on npm (`next`), on GHCR (amd64 + arm64) and running on TEST. PROD is
untouched on `3.1.0`. The suite passed 120/120 on TEST with no performance regression; the verdict is
**promote**. Nothing was merged.

Two things are worth reading beyond the mechanics:

1. **The RC needed no merge.** Last time it took two (enter pre mode, then Version Packages). A tag is
   enough: `release.yml` takes the version from the tag name.
2. **The poller could not have deployed any RC.** `meteoswiss-deploy.sh` edits the wrong compose line,
   silently. Found, worked around for TEST, not fixed.

## 1. The RC route

#157's head (`398c004`) is `main` plus one commit (version bump, CHANGELOG, the consumed changeset).
`src/` is identical to `3.1.0`; the release is a dependency refresh (SDK 1.32.1, jsdom 30, js-yaml,
express and friends).

The workflow does not need `package.json` to carry the RC version: it derives the version from the tag
and runs `npm version` itself when they differ; a `X.Y.Z-*` tag publishes to npm `--tag next` and GHCR
`:<version>` only, so `latest` cannot move. There is no `.changeset/pre.json`, so `-rc.0` is also what
changesets would have produced.

```
gh release create meteoswiss-mcp-v3.1.1-rc.0 --prerelease --target 398c004 \
  --title "meteoswiss-mcp v3.1.1-rc.0" --notes-file <notes>
```

Pre-flight: #157's PR CI was `action_required` (the bot-CI gate, as before); `gh run rerun` re-ran it
under a real identity and all five jobs passed, including Docker Build Test. Release workflow: CI
Validation, Publish to npm, Publish to GHCR all green. `npm view` → `next=3.1.1-rc.0`, `latest=3.1.0`.

Entering pre mode "to be faithful to last time" would have meant merging to `main`, which the brief
rules out without a report first, and would have produced the same artifacts.

## 2. Why the TEST deploy failed

The LaunchAgent is loaded (300 s, `last exit code = 0`) and detected the RC at 16:47. Its deploy
rolled back every cycle: "Restarting…" → compose prints only `Container meteoswiss_mcp_server_test
Running` → 12 health checks of `version mismatch (got 3.1.0, want 3.1.1-rc.0)`.

Homebot handed over the log (blocked for this session by `.ckignore`) with two hypotheses; both were
checked rather than assumed:

| Hypothesis | Check | Result |
|---|---|---|
| (b) RC image reports 3.1.0 | throwaway container from the RC image | `/health` and `package.json` both say 3.1.1-rc.0 → **ruled out** |
| (a) compose did not recreate | `docker events` during an attempt; StartedAt | no stop/create/start; StartedAt unchanged since 09-24 → **confirmed** |

(a) was the symptom, not the cause. The cause: `set_compose_image` finds the line with
`yq '<path> | line'`, and on the current compose file yq returns 237 (TEST) and 210 (PROD) where the
real lines are 242 and 215. `sed '237s|…|…|'` matches nothing and exits 0, the guard passes, and
compose has no change to apply. The rollback is the same function, so it fails the same silent way.
Lines 237 and 210 are a comment and a volume entry, so nothing was damaged.

An interactive `docker compose up -d --dry-run` against a scratchpad copy with the right line edited
printed `Recreate`, which is what separated "compose is fine" from "the file never changed".

I did not find why yq's numbering is off by 5; I stopped at the line numbers being wrong.

**Workaround, TEST only:** edited line 242 with an exact `sed`, ran `docker compose up -d
meteoswiss_mcp_server_test`, waited for `/health` = `3.1.1-rc.0`. The next poller cycle printed
"Already running", exited 0 and wrote `meteoswiss-mcp-v3.1.1-rc.0` to the state file, which is the
behaviour a working deploy would leave behind.

I did not edit the script: the poller executes it every 5 minutes, bash reads scripts incrementally,
and this is the script that once rewrote PROD's tag. Proposed fix is in the report (find the line by
the service header, then verify the result with `yq` and abort if it differs).

## 3. Testing

Claude Code's own `meteoswiss-mcp-test` connection exposes no timing and had been opened against the
old container, so the suite is a small dependency-free Node client (the worktree has no
`node_modules`) that speaks Streamable HTTP and records time to first byte per call. These servers
answer with a single JSON body, so TTFT equals total time.

- **The jsdom major bump** was the main risk and is not in the changelog. The same 27 pages (taken from
  live `search` results in four languages and four content types) were fetched on PROD 3.1.0 and
  TEST 3.1.1-rc.0 and diffed: 27/27 identical, 47/47 comparable payloads identical overall.
- **The SDK bump** shows up in one place: validation error text is now compact instead of an embedded
  JSON array. Same `isError`, same code. Not in the changelog.
- **Rate limit:** 100 req / 60 s, JSON 429, standard `ratelimit-*` headers, recovers after the window.
- **Performance:** sequential timings in the report. The first 8-way forecast wave on TEST took ~110 s,
  against 79–87 s recorded on 09-11. The host was busy (load average 5.7 → 9.6), so a controlled A/B was
  run with identical throwaway containers of 3.1.0 and 3.1.1-rc.0 alternating: 116 s / 157 s vs
  115 s / 105 s. No regression.

### Things that went wrong in the testing

- **My first fetch tests failed on every page.** I had guessed URLs; eight "failures" on PROD were
  164-byte "Content not found". The suite now takes its page list from live `search` results and
  reuses one saved list for both servers.
- **I used the wrong parameter name.** `fetch` takes `id`, not `url`; the rc4 report is stale on that.
  Found by reading `tools/list` instead of guessing a second time.
- **Four false failures on the throwaway RC container** were the rate limiter reacting to my ~100-call
  burst, not climate data. The suite now waits out the window and counts retries.
- **Port 23080 is Grafana**, and my first throwaway container could not bind it; the "health" I read
  was a login redirect. Spare loopback ports were used after that.
